## 实施日期

## 问题描述
用户反馈：拖动节点虽然快了，但不够丝滑，像帧率不够，有掉帧感觉。

## 根本原因分析

根据 `节点拖动性能问题-完整诊断.md` 的分析，发现以下性能瓶颈：

### 瓶颈 1：每次 mousemove 都触发 React 重渲染 ⚠️
```typescript
setMousePos({ x: clientX, y: clientY });  // ❌ 每次 mousemove 都更新 state
```
**影响**：每秒 60+ 次 React 重渲染，导致严重卡顿

### 瓶颈 2：拖动节点时每次都触发 setNodes ⚠️
```typescript
setNodes(prev => {
    const newMap = new Map(prev);
    const node = newMap.get(draggingNodeId);
    if (node) {
        newMap.set(draggingNodeId, { ...node, x: proposedX, y: proposedY });
    }
    return newMap;
});
```
**影响**：每次 mousemove 都触发整个组件树重新渲染

### 瓶颈 3：Resize 时每次都触发 setNodes ⚠️
```typescript
setNodes(prev => {
    const newMap = new Map(prev);
    const node = newMap.get(resizingNodeId);
    if (node) {
        newMap.set(resizingNodeId, { ...node, width: ..., height: ... });
    }
    return newMap;
});
```
**影响**：每次 mousemove 都触发整个组件树重新渲染

### 瓶颈 4：Group 拖动时每次都查询 DOM 和更新 state ⚠️
```typescript
childNodes.forEach(child => {
    const nodeElement = document.querySelector(`[data-node-id="${child.id}"]`);  // ❌ 每次都查询
});
setNodes(prev => { ... });  // ❌ 每次都更新 state
```
**影响**：如果 Group 有 10 个子节点，每次 mousemove 查询 10 次 DOM + 触发重渲染

## 完整修复方案

### 修复 1：使用 ref 存储鼠标位置 ✅

**修改位置**：`App.tsx` - 添加 ref

```typescript

// 性能优化：使用 ref 存储 scale 和 pan，减少 useCallback 依赖项
const scaleRef = useRef(scale);
const panRef = useRef(pan);

useEffect(() => {
    // 性能优化：同步 scale 和 pan 到 ref
    scaleRef.current = scale; 
    panRef.current = pan;
}, [scale, pan]);
```

**修改位置**：`App.tsx` - `handleGlobalMouseMove`


## 技术原理

### 为什么直接操作 DOM 更快？

1. **避免 React 重渲染**：
   - `setNodes()` 会触发整个组件树重新渲染
   - 直接操作 DOM 只修改单个元素的样式

2. **使用 CSS transform**：
   - `transform` 不触发 reflow，只触发 repaint
   - GPU 加速，性能极佳

3. **缓存 DOM 查询**：
   - `querySelector` 是昂贵的操作
   - 缓存后只查询一次

4. **延迟 state 更新**：
   - 拖动过程中不更新 state
   - 只在结束时更新一次

### 为什么要恢复 transition？

1. **拖动过程中禁用 transition**：
   - 避免动画延迟，实现即时响应

2. **拖动结束后恢复 transition**：
   - 保持其他交互的平滑动画
   - 使用 `requestAnimationFrame` 确保在下一帧恢复
